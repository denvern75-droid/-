# 토큰 절약·효율 운영 지침 (바이브코딩)

## 0. 지위·목적
- 목적: AI 코딩·자동화 작업의 **토큰·비용·컨텍스트 낭비를 줄이는 표준**을 정의함
- 구성: §1 즉시 적용 원칙(Claude가 매 작업에서 준수) + §2 외부 도구 카탈로그(사용자가 도입 검토)
- 출처: 영상 「바이브코딩하다가 거덜나기 싫으면 무조건 보세요」(https://www.youtube.com/shorts/1HZe14zd6nQ) 요약본(2026-09-18 확인)
- 원칙 충돌 시: 정확성·안전이 토큰 절약보다 우선함(절약이 품질·검증을 훼손하지 않음)

## 1. 즉시 적용 원칙 — Claude가 매 작업에서 준수
영상 5개 도구의 핵심 원리를 도구 설치 없이 바로 적용 가능한 규칙으로 환원함.

### 1.1 코드 최소주의 (Ponytail 원리)
- 코드 생성 전 4단 판단 순서를 따름
  1. **만들 필요가 있는가** — 요구를 실제로 충족하려면 새 코드가 필요한가
  2. **기존 코드가 있는가** — 프로젝트 내 재사용 가능한 함수·모듈이 있는가
  3. **표준 기능으로 가능한가** — 언어·런타임 표준·이미 설치된 의존성으로 되는가
  4. **최소 구현은 무엇인가** — 가장 작은 변경으로 목표를 달성하는 방법
- 금지: 불필요한 라이브러리 추가, 과도한 보일러플레이트, 요구되지 않은 기능 선반영

### 1.2 컨텍스트 절약 (Headroom 원리)
- 대량 로그·도구 출력·파일 전문을 **요약·발췌**해 다루고, 원문은 경로·참조로 남김
- 반복 붙여넣기 대신 필요한 구간만 인용함
- 검색 결과·RAG 자료는 관련 부분만 취해 컨텍스트에 올림

### 1.3 의미 기반 탐색 (Serena 원리)
- 큰 코드베이스는 전체 통독을 지양하고 **심볼(함수·클래스·변수) 단위**로 필요한 부분만 탐색·편집함
- 파일 전체 재출력보다 대상 구간만 수정함

### 1.4 세션 기억 절약 (Claude-Mem 원리)
- 이전 작업을 매번 장황히 재설명하지 않도록 **핵심 결정·상태를 간결히 기록**하고 참조함
- 연속 작업은 '무엇을·왜·다음 할 일'만 요약 유지함

### 1.5 사용량 관리 (UsageScope 원리)
- 한도·초기화 시각을 인지하고 **작업 시점·모델 선택을 조절**함(도구 자체는 절감이 아니라 관리 목적)

## 2. 외부 도구 카탈로그 — 사용자 환경 도입 검토용
> 벤치마크 수치는 **각 저장소의 개발자 자체 측정치**이며, 실제 효과는 작업·환경에 따라 달라짐(수치 무결성 원칙상 확정값으로 인용 금지).

| 순서 | 도구 | 유형 | 주된 역할 | 직접 토큰 절감 | 사용자 추천도 |
|---|---|---|---|---|---|
| 1 | UsageScope | 사용량 모니터 앱 | 사용량·한도·초기화 시각 확인 | 낮음(관리용) | 높음 |
| 2 | Ponytail | 코딩 스킬·플러그인 | 불필요한 코드 생성 억제 | 높음 | 중상 |
| 3 | Headroom | 문맥 압축 계층 | 입력 문맥·로그·파일 압축 | 높음(긴 작업) | 중간 |
| 4 | Serena | 코딩 MCP 도구 | 의미 기반 코드 탐색·편집 | 중간(간접) | 중간 |
| 5 | Claude-Mem | 기억 플러그인 | 세션 간 기억 저장·검색 | 중간(재설명 감소) | 매우 높음 |

- 공식 링크
  - UsageScope: https://www.usagescope.com/
  - Ponytail: https://github.com/DietrichGebert/ponytail
  - Headroom: https://github.com/headroomlabs-ai/headroom
  - Serena: https://github.com/oraios/serena
  - Claude-Mem: https://github.com/thedotmack/claude-mem
- 유의: 다섯이 모두 '스킬'은 아님 — 앱·플러그인·압축 계층·MCP·기억 플러그인이 섞여 있으므로 설치 방식이 각각 다름

## 3. 도입 우선순위 (Windows·Hermes·Codex 환경 기준)
1. **UsageScope(Windows판)** — 현재 Claude·Codex 등 사용량·초기화 시각부터 확인함(가장 간단)
2. **Claude-Mem** — 여러 날 이어지는 연속 작업이 많으므로 재설명 비용 절감 효과가 가장 큼(설치 충돌 여부 점검)
3. **Ponytail** — 앱·자동화 코드 생성 시 시험 적용해 코드량·오류·토큰을 전후 비교함
4. **Serena** — 자동화 코드가 여러 파일로 커진 뒤 필요한 함수·파일만 탐색하도록 도입함
5. **Headroom** — 장시간 로그·대규모 문맥으로 비용이 계속 커질 때 별도 시험 프로젝트에서 검증함

## 4. 도입 리스크·수칙
- **동시 설치 금지**: 5개를 안정 운영 중인 자동화에 한꺼번에 붙이면 충돌 원인 파악이 어려움 → **1개씩 설치·전후 비교**
- **효과 미보장 구간**: 짧거나 이미 압축된 작업에는 압축·기억 도구 이점이 작음
- **설정 복잡성**: Headroom(로컬 프록시·Python)·Serena(공식 Quick Start 우선) 등은 시스템 구성 부담이 있음 → 시험 환경에서 검증
- **총비용 주의**: Claude-Mem 등은 색인·요약 처리에도 자원이 들어 모든 상황에서 총절감이 보장되지 않음
- **연결·권한**: UsageScope는 서비스별 계정 연결·API 키·로컬 사용기록 접근이 필요할 수 있음

## 5. 갱신(업데이트) 절차
1. 새 도구·버전·벤치마크 근거 확보 시 출처 기록
2. 변경 항목 특정 → 해당 절만 최소 수정
3. frontmatter `version` 상향(오탈자=PATCH / 항목 추가=MINOR / 체계 개편=MAJOR)
4. `CHANGELOG.md`에 날짜·버전·요지·근거 개조식 기록
5. 벤치마크 수치는 '개발자 자체 측정치' 표기 유지
